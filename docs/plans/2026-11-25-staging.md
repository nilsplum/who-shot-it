## 2. How it is today, and what the standard is

- **One server**: the Worker `who-shot-it` on `who-shot-it.nils-plum.workers.dev`
  (`wrangler.jsonc`, `SERVER.origin`), live as Cloudflare version 9226b0f0 (commit 847b99b,
  23 November). Apple's reviewer of 1.0.5, every TestFlight build and the website all use it.
  No staging environment, no preview URLs.
- **The apps carry the address**: `phone.serverOrigin` maps the app's own page origins
  (`SERVER.appOrigins`) to `SERVER.origin`; anywhere else (the website, `./scripts/dev.sh`
  with live reload, the tests) the page talks to the origin it came from. `index.html`'s
  Content-Security-Policy restates the address.
- **One build per version**: `release-apps.sh` builds every upload against the one server;
  the build number is the version as a number (1.0.9 is 10009). An upload reaches TestFlight's
  team group at once; `--submit` sends the same build to App Review.
- **Starlabs** (`/Users/nils/Starlabs-MVP`, read for its scripts): one table of the deployed
  environments (`scripts/helpers/environments.sh`: each one's name and address, `development`
  deliberately absent because it is local); every entry script takes the environment as an
  explicit flag and refuses without one (`--local-backend`, `--remote-backend-staging`,
  `--remote-backend-production`); a build gets the address written into its env files by one
  writer from that table and asserts it; every production step asks for a typed phrase that
  can be given in advance with `--confirm "<exact phrase>"`; production artifacts come from
  `main`.
- **The stores**: Apple reviews exactly the binary that was uploaded, and every upload also
  lands in TestFlight; a build number may be used once per version. Google takes uploads on a
  track (internal or production) and needs version codes that only grow. Cloudflare's
  documented way to a second copy of a Worker is a Wrangler environment: `env.staging` becomes
  the Worker `who-shot-it-staging` with its own workers.dev address and its own Durable
  Objects (its own rooms and photos); bindings are not inherited and are repeated there.

## 3. The design

- **Three environments, two of them deployed**: *local* (`./scripts/dev.sh`, the tests:
  `wrangler dev` on this computer, as today), *staging* (the test builds: TestFlight, Google
  Play's internal track; the Worker `who-shot-it-staging`) and *production* (the store apps,
  the website, the store links; the Worker `who-shot-it`, unchanged). No cloud dev server:
  local already is one.
- **One table**: `ENVIRONMENTS` in `web/shared/config.js`, the deployed environments with their
  address, their Worker and their build-number digit; the app, the server and the scripts read
  it. `wrangler.jsonc` restates the Worker names (Wrangler's own format) and `index.html` the
  addresses (a static page); `test/unit/config.test.js` pins both to the table.
- **A build knows its environment** from `web/js/environment.js`, which says `production`.
  Only `release-apps.sh` changes it, in the native project's copy of the game, for the one
  build it makes, checks it, and puts the copy back afterwards; so anything built any other
  way can only be production. `phone.serverOrigin` picks the address from the table.
- **The build number carries the environment**: the version as a number, times ten, plus the
  environment's digit (1.0.9 is 100090 for staging, 100091 for production). App Store Connect
  shows which is which, the same version can be tested on staging and then released, and App
  Review can only ever get a production build (`--submit` looks for the production number).
  Android's version code is the same number, so it keeps growing.
- **Scripts with explicit environments** (no default, nothing to get wrong by forgetting):
  `./scripts/deploy.sh staging|production` and `./scripts/release-apps.sh staging|production
  [ios] [android] ...`. Staging uploads go to TestFlight (team and public link) and Google
  Play's internal track, never further. Production needs a clean `main` and a typed phrase for
  what reaches people (a production deploy, App Review, Google Play's production track);
  `--confirm "<phrase>"` gives it in advance. `release-apps.sh status` shows where the stores
  stand. The test players find the game on staging or production by themselves.

## 4. Things to pay attention to

- The production Worker's name and address must never change: the installed apps have it
  built in. Staging is added beside it.
- Staging and production share the free plan's daily quota; staging is used by one person.
- A staging build and a production build never meet: their rooms are on different servers
  (an invite from a TestFlight phone does not work for an App Store phone).
- The production server keeps understanding every app version in use, as before; staging may
  run ahead of it.

## 5. Not part of this plan

- A separate staging app (another bundle id), which the operator decided against.
- Moving the test players' script into `scripts/` (it stays a helper with its guide).

## 7. Decision log

(Dated entries, added while implementing.)

**25 November 2026, commit 2 (the environments)**

- **Production stays wrangler.jsonc's top level**, under its name `who-shot-it`: its address
  is built into every installed app, and a plain `wrangler dev` (the tests, `./scripts/dev.sh`)
  keeps running the same configuration. Cloudflare's docs show the top level as development
  with named staging and production environments; renaming production would have moved its
  address. Staging is `env.staging`, which Wrangler deploys as `who-shot-it-staging`.
- **The staging Durable Object binding is repeated** (Wrangler does not inherit bindings),
  **and so is its migration**: the configuration reference lists migrations as inherited, the
  Durable Objects page says an environment's own override the top level's; stating it in both
  places is true either way, and the test keeps the two equal. A dry run
  (`wrangler deploy --env staging --dry-run`) built it with its own Room binding.
- **Both addresses are in the app's Content-Security-Policy**: a production build may reach
  staging's address and the other way round. Both are ours; one policy for every build keeps
  `index.html` free of a build step.
- **The table is ordered production, staging**, and the policy lists them in that order (the
  test builds the expected policy from the table).
- **The test players look on staging first**, then production: a TestFlight phone is the
  usual reason to call them; a code unknown to staging is looked up on production, any other
  answer (a full game) ends the search. `staging`, `production` or an address picks one.
- **The build number's digit lives in the table** (`build`), and `buildNumber` is the one
  formula; the scripts and the App Store Connect helper use it in the next commit.

**25 November 2026, commit 3 (the scripts)**

- **The environment is a word, as the other scripts' targets are** (`./scripts/dev.sh ios`,
  `./scripts/deploy.sh staging`), not a Starlabs-style `--remote-backend-staging` flag: one
  required word per run, checked against the table (`check_environment`), no default.
- **Typed phrases, asked before the long part** (the tests and the build take minutes):
  "deploy to production", "submit <version> to App Review", "release <version> on Google
  Play", "take it back from App Review". As in Starlabs, `--confirm "<phrase>"` gives one in
  advance and only that exact phrase counts; there is no blanket `--yes`. Without a terminal
  and without the phrase, the step refuses.
- **Production only from a clean `main`** (`check_production_source`), deploys and builds
  alike; staging from any branch, so a branch is tried there before it is merged.
- **A staging iPhone upload goes to the public TestFlight link by itself** (the operator: team
  and public link; nobody but the operator uses TestFlight). A production upload without
  `--submit` stays with the team, to be tried and recorded; `--submit` then sends exactly that
  build (found by its number) instead of building again, so the reviewed build is the
  recorded one.
- **An iPhone upload asks App Store Connect first** (`app-store.mjs uploaded`): a version
  already uploaded for that environment stops before ten minutes of building, with the fix.
- **The environment decides Google Play's track** (staging internal, production production);
  `--android-track` is gone. A release bundle built without the script's number refuses to
  build (`android/app/build.gradle`), so none reaches Google Play by hand.
- **Builds only for a server that answers** (`check_server_up`): a staging build before the
  staging Worker exists stops with "deploy it first".
- **`status` and `withdraw` are modes of `release-apps.sh`**: `app-store.mjs` and
  `play-upload.mjs` are only ever run by it now.
- **The native copy goes back to production after every build** (an EXIT trap runs
  `npx cap copy`), so a build later made in Xcode or Android Studio by hand can only be
  production.
- **AGENTS.md**: both deploys, every upload and `withdraw` are critical commands for an agent;
  the typed phrase is a second guard, given in advance only for the step the operator
  approved.
- **Checked by hand** (the scripts have no automated tests): every refusal (no or an unknown
  environment, two at once, staging with `--submit`, `--submit` without the upload, a mode
  with a platform, an unknown option, production from a branch), a phrase given in advance
  and a missing one without a terminal, the staging server's check before it existed, and the
  build numbers.
